# 성취수준 E2E 사전 검증 후 수정 계획 — 2026-09-20

후속 구현 및 실제 검증 결과는 [RC4 검증 기록](achievement-rc4-validation-2026-09-20.md)에 정리한다. 아래 내용은 수정 착수 전 계획이며, 당시 상태와 완료 기준을 보존한다.

이 문서는 [사전 검증 보고서](achievement-e2e-preflight-2026-09-20.md), 현재 제품 코드, 로컬에 보존된 진단 자료를 대조한 수정 계획이다. 제품 수정·원격 재실행·배포·출시 승인은 이번 작업에서 수행하지 않았다. 기준 HEAD는 `df5efee6b5eccced210cdad04064e5ab51893e86`이며, 기존 작업 트리의 보고서·수집기·README 변경은 보존한다.

핵심 결론은 **게시판 발견 → 상세·첨부 확인 → 안전한 다운로드를 먼저 연결하고, 실제 원문으로 추출 결함을 확인한 뒤 새 RC 전체를 평가한다**는 것이다. 현재 NO-GO 판정은 유지한다. 경로 지원만으로 추출 정밀도나 출시 조건을 충족했다고 판단할 수 없다.

## 2. 1단계 — 공식 게시판 계약과 안전한 전송 확정

**작업**

- 보존된 `evals/results/e2e-20260920/catalog-collector.mjs`와 공개 사이트 근거를 출발점으로 목록 API의 요청·응답, 실제 페이지 정보, 학교급·교과 필터를 재확인한다. 현재 저장된 수집기는 두 페이지를 고정 조회하므로 제품 발견 알고리즘으로 그대로 옮기지 않는다.
- 화면 경로 `/cmnBoard/list/57` 및 `/cmnBoard/view/57/{pstId}`와 API의 `bbsId=19` 매핑을 명시한다. 상세 API의 정확한 경로·메서드·본문·응답 구조·첨부 소속 필드는 재확인 후 고정한다. 아직 확인하지 않은 상세 endpoint 이름을 추측하여 구현하지 않는다.
- 목록 전송은 어댑터가 만든 고정 JSON 스키마와 크기 제한만 허용한다. MCP 입력이 임의 URL·메서드·헤더·본문을 선택할 수 없도록 한다.
- 기존 DNS/IP 검증, 연결 주소 고정, TLS, 요청·압축해제 크기 및 시간 제한, 취소 전파를 유지한다. POST 리디렉션은 우선 거절하고 공식 동작상 필요성이 확인되면 허용 목적지와 메서드 유지 규칙을 별도 테스트한다.
- 검증한 최소 메타데이터만 fixture로 만든다. 원문·임시 서명 URL·비밀값은 공개 fixture에 넣지 않는다. 독립 정답 카탈로그를 제품의 정답 조회표로 사용하지 않는다.

**완료 기준**

목록·상세 계약과 메뉴/게시판 매핑이 재현 가능하고, 잘못된 게시판 ID·본문·호스트·리디렉션은 거절된다. 기존 GET 상세·다운로드 메타데이터 경로도 유지된다.

## 3. 2단계 — 발견·상세·첨부 경로 연결

**작업**

- 게시판 목록 어댑터를 별도 모듈(예: `src/achievement/official-listing.ts`)로 구현하고 검색 orchestrator에서 호출한다. 공식 검색이 0건이어도 목록 경로를 시도한다. 어느 한쪽이 실패하면 성공한 경로의 결과와 실패 범위를 함께 반환한다.
- `registry.enabled=false`는 목록과 상세 네트워크 접근을 모두 중단해야 한다. 목록은 첨부 메타데이터까지만 읽으며 문서 다운로드·Worker 실행을 하지 않는다.
- 게시판 응답을 기존 `ResourceIdentity`/`ResourceDetails`로 변환한다. `pstId`, 제목, `atchFileList` 등 실제 계약 필드를 명시적으로 매핑하고 숨김·삭제·소속 불일치 첨부를 제외한다. 첨부 URL은 검증된 `fileRscId`로 공식 다운로드 API 주소를 생성한다.
- 메인과 Worker가 같은 상세 어댑터로 첨부 소속을 다시 확인하도록 한다. 검색에서만 게시판을 지원하고 Worker의 재조회는 실패하는 상태를 방지한다.
- `resourceDetailUrl()`의 기존 나머지 분기는 모두 `conts` endpoint를 생성하므로 경로별 명시적 분기로 바꾼다. 후보 중복 키도 endpoint 종류·게시판 ID·게시물 ID를 포함하여 동일 숫자 ID의 다른 자료가 합쳐지지 않도록 한다.
- 학교급·교과·제목 일치도는 실제 메타데이터에 근거하여 순위에 반영한다. 코드 질의는 검증된 코드 체계에서 얻을 수 있는 탐색 단서로 질의를 넓힐 수 있지만, 원문에 없는 `codeHint`나 특정 학년을 만들어 넣지 않는다. 예를 들어 `[9과05-01]`을 중2로 단정하지 않는다.
- 자연어 질의 전체를 제목 필터에 넣어 재차 0건이 되지 않도록 제한된 질의 완화를 설계한다. 코드만 묻는 경우와 ‘힘의 평형’처럼 제목에 없는 개념을 묻는 경우도 교과 성취수준 문서 후보에 도달하는지 확인한다.
- 10초 전체 예산 안에서 목록·기존 검색·상세 조회 시간을 배분하고 목록 페이지/후보 수를 제한한다. 학교급·교과 필터링을 상위 20건 제한 전에 적용한다. 전체 목록을 매 요청마다 무제한 수집하지 않는다.
- 검색 API와 게시판의 페이지 범위가 다름을 `coverage`에 기록한다. 출처별 시도·성공·실패·잘림 상태와 다음 페이지 근거를 구분한다. 통합 페이지가 생략 후보를 복구하지 못하면 `nextPage`를 내지 않는다.
- 현재 `successes`는 검색 API 성공 횟수다. 목록 성공도 상태 계산에 반영한다. 일반 검색 인증 누락과 공개 목록 성공을 구분하고, 확인한 범위에서 미발견이라는 표현을 유지한다. 응답 스키마 변경 시 성취수준 도구 계약·테스트·문서를 함께 갱신한다.

**완료 기준**

- 기존 검색을 0건으로 고정한 회귀 검사에서도 게시판의 중학교 과학 자료 `602681`을 발견한다.
- 보존된 세 질의에서 기대 문서와 PDF/HWP 첨부를 반환하고, 검색이 발급한 참조로 읽기 목록까지 이어진다.
- 다른 교과·게시판·자료 ID 충돌, 목록의 후속 페이지, registry 비활성화, 한쪽 API 장애·취소에 대한 회귀 검사를 통과한다.
- 일반 `search_edunet`의 입력·출력 계약과 첨부 다운로드 0회 특성을 유지한다.

## 4. 3단계 — 다운로드 연결과 실제 원문 추출 진단

**작업**

- 공식 다운로드 API가 반환하는 호스트와 `/KEDNCM/NCIC/tchboard/10055/`를 재확인한다. 관측으로 뒷받침되는 최소 경로군과 PDF/HWP/HWPX 확장자만 허용한다. `/KEDNCM/**` 전체 허용으로 확장하지 않는다.
- 허용 경로의 인접 폴더, 이중 인코딩·경로 탈출, 외부 호스트·사설 IP·리디렉션, MIME/확장자/magic 불일치가 계속 차단되는지 검사한다.
- 10MiB 제한은 유지한다. 읽기 목록에서 이미 알려진 초과 크기는 사유와 함께 읽기 불가로 안내한다. 실제 전송 시 크기 검증도 유지하고 크기 미상 자료를 성공 가능하다고 보장하지 않는다. 검색 후보의 안내와 읽기 목록의 안내가 모순되지 않도록 조정한다.
- `scripts/verify-remote.mjs`의 광범위 검색 후 첫 첨부 선택을 고정된 대조 자료·파일 식별 방식으로 바꾼다. 목표 자료가 없거나 읽기에 실패하면 그 사실을 기록하고 실패 처리하며, 다른 성공 첨부로 조용히 대체하지 않는다. 대용량 거절은 별도 예상 실패 사례로 검증한다.
- 실제 MCP 검색 → 목록 → 선택한 첨부 → Worker → 모든 cursor를 통한 읽기로 과학 PDF에 도달한다. 원문 해시, PDF 28쪽/인쇄 24쪽, `[9과05-01]`, A–E 설명과 병합 셀 관계를 독립 정답에 대조한다. PDF 페이지와 인쇄 페이지를 혼용하지 않는다.
- 실제로 잘못 읽은 경우에만 `src/worker/parsers`, `src/worker/intermediate`, `src/worker/achievement`, `config/document-profiles`를 수정한다. 코드·수준·설명 누락, 반복 머리글, 병합 셀, 옆 성취기준으로의 설명 유출을 구분하고 최소 회귀 fixture를 추가한다. 확인 불가능한 관계는 추정하지 않고 보수적 상태를 유지한다.

**완료 기준**

목표 원문의 다운로드·파싱 단계까지 도달하고 추출 결과를 평가할 수 있다. 텍스트 읽기 성공과 구조화 추출 통과는 별도로 판정한다. `metadata_only` 또는 추출 오차가 남으면 원인을 기록하고 정식 RC 고정 전에 필요한 수정을 마친다. 병합 셀 정답의 최종 판정은 사람 검토가 필요하다.

## 5. 4단계 — 평가 수집기와 배포 식별 보강

**작업**

- 기존 `achievement-remote-probe.mjs`는 진단용으로 보존하고 별도 acceptance 실행기·스키마·채점기를 준비한다. 제품 개발 진단과 출시 평가의 결과를 합산하지 않는다.
- 발견의 다음 페이지/제한 도달, 첨부 목록의 페이지 제한, cursor 반복·소실·불일치, MCP `isError`, 네트워크 실패를 단계별로 기록한다. 현재 수집기는 발견 첫 응답만 검사하고 첨부 최대 10페이지·본문 최대 20페이지에서 멈추므로, 한도 종료를 미발견이나 정상 완료로 취급하지 않도록 한다.
- 다운로드·파싱·추출·evidence·모델 최종 답변을 분리하여 저장하고 분자·분모·미도달·미측정 사유를 남긴다. 모델 평가가 필요한 시나리오는 사전 고정 도구 인자 실행과 별도 모드로 수행한다.
- 출력 덮어쓰기 거절, 서명 참조/비밀값 마스킹, 사전 정답 해시와 실행 식별자 보존을 유지한다. 의미 채점·사람 검토 전에는 `releaseEligible:false`다.
- `scripts/build-vercel.mjs`에 소스 SHA·패키지/lockfile·registry/profile 해시를 담은 비밀값 없는 빌드 manifest를 포함하고 bundle 검사에서 확인한다. 원격 검증이 읽을 수 있는 최소 배포 식별 정보 제공 방식을 구현한다.
- 고정 소스에서 만든 산출물과 실제 배포 ID를 연결하고, 원격에서 관측한 manifest를 검증한다. 패키지 버전만 같거나 로컬 SHA를 보고서에 복사한 것으로 동일 배포를 인정하지 않는다.

**완료 기준**

실패·부분 수집·배포 불일치·미검토 결과가 통과로 집계되지 않는다. 동일 버전의 다른 소스 배포를 식별하고 차단할 수 있다. 수집기 테스트는 네트워크 없이 페이지 종료·오류·마스킹·분모 처리를 검증한다.

## 6. 5단계 — 새 RC와 전체 acceptance 평가

**진행 순서**

1. 개발 중 원문 진단을 마친 뒤 새 후보의 소스·의존성·플래그·registry/profile·빌드 산출물을 고정한다. 기존 검색 전용 `v1.0.0-rc.1` 기록을 재사용하지 않는다.
2. 독립 원문 기반 30개 문서와 문서별 약 3개, 전체 약 90개 시나리오를 완성한다. 초등 표본은 다른 공식 교육과정 게시판을 조사하여 보완하고, 학교급·교과·난이도·PDF/HWP 분포와 선정 기준을 실행 전에 고정한다. 발견 조사에 필요한 추가 경로는 별도 검증 후 registry에 넣는다.
3. 스캔·지원하지 않는 형식·크기 초과·복잡한 병합·다학년·문서 자체 수준 라벨의 기대 동작을 별도로 정의한다. 정상 문서 정확도와 예상 실패 처리를 구분한다. 읽기 쉬운 파일만 사후 선택하거나 인덱스 부재가 미확정인 실패를 분모에서 제외하지 않는다.
4. 같은 소스의 검증용 원격 배포에서 소수 연결 검사를 수행한 뒤 전체 corpus를 처음부터 실행한다. 과거 진단 3건은 전체 실행 건수에 합산하지 않는다. 원문 직접 획득은 정답 작성에만 쓰며 제품 발견 성공은 실제 Remote MCP 경로로 확인한다.
5. 원문·정답·실제 출력·rubric을 제공하는 독립 평가와 사람 검토를 진행한다. `HUMAN_REVIEW_REQUIRED` 건의 사람 판정을 모델이 대신 작성하지 않는다.
6. 운영과 유사한 격리 검증 배포에서 만료 참조, Worker crash/timeout, circuit breaker, 반복 호출 및 cold start를 확인한다. 읽기 실패 후 같은 연결의 일반 검색 복구를 검증한다. 운영 공개 서버에 장애를 주입하지 않는다.
7. 제품을 변경하면 새 후보·해시를 만들고 전체 평가를 재실행한다. 결과와 rollback 절차를 정리하여 공개 배포 판정 자료로 제출한다.

**판정 기준**

보고서에 명시된 구조화 추출 정밀도 ≥98%, evidence 원문 존재율 100%, 치명적 오류 0건은 모두 실제 측정과 충분한 표본이 필요하다. discovery/attachment/parse 등의 수치 기준과 최종 Gate 문구는 이번에 제공된 보고서만으로 확정할 수 없다. 누락된 원계획의 최종 기준을 회수하거나 별도 기준을 확정한 후 acceptance 실행에 사용한다. 기존 일반 검색 평가의 81/90 기준을 성취수준 평가에 가져오지 않는다.

## 7. 변경 묶음과 검증

| 변경 묶음 | 핵심 산출물 | 검증 |
|---|---|---|
| A: 게시판 계약·메타데이터 전송 | 고정 API 계약, 제한적 POST, 최소 fixture | `safe-download`, 게시판 어댑터 신규 테스트 |
| B: 발견·상세·첨부 | 목록 통합, 소속 검증, 적합도·coverage·페이지 처리 | `achievement-discovery`, `achievement-read`, `reference-scope`, 취소·adversarial 검사 |
| C: 원문 다운로드·실패 안내 | NCIC 최소 경로 지원, 크기 안내, 결정적인 remote smoke | `safe-download`, 실제 MCP 읽기, 필요시 parser 회귀 |
| D: 평가·배포 동일성 | acceptance 실행기/채점기, build manifest, 검증 문서 | 실행기 오류·부분 완료 테스트, `vercel-bundle`, 원격 SHA 불일치 검사 |
| E: 후보 고정·전체 평가 | 새 RC, 독립 corpus, 원격 실행·사람 검토·장애 검증 기록 | 전체 acceptance 및 공개 배포 판정 |

의존 순서는 **A → B → C → 후보 고정 → 전체 평가**다. D의 실행기·배포 식별 준비와 독립 corpus의 수집은 개발과 병행할 수 있지만, 전체 평가는 제품·평가기·정답·원격 배포를 고정한 후 시작한다. 원문 진단에서 추가 결함이 확인되기 전에는 parser 수정 규모나 전체 완료 일정을 확정하지 않는다.

제품 변경 후 `npm run check`, `node --test evals/tests/*.test.mjs`, `npm run eval:contract -- --out evals/results/NEW-RUN/contract.json`, `npm run eval:achievement`를 실행한다. 원격 검증 전 build/bundle에 새 어댑터·registry·manifest·Worker가 포함됐는지 확인한다. 기존 golden 실행기의 출력 경로 정책을 확인하고 과거 결과를 별도 보존한다. 사전 보고서의 203/203·63/63은 당시 결과이며 새 소스의 검사 결과로 재사용하지 않는다.

제품 지원 문서 `achievement-sources.md`, `achievement-implementation.md`, `vercel-deployment.md`, `evals/README.md`는 각 구현이 검증된 시점에 갱신한다. 원래 사전 검증 보고서와 결과 파일은 당시 관측 기록으로 보존한다.
